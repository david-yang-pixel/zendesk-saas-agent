## 代码缺陷类工单处理策略

### 检索优先级调整

- **优先**：源码分析 — 必须创建 worktree（`sandbox_create_worktree`），在完整代码树中定位问题
- **辅助**：`git_diff` 对比当前版本与上一版本的差异，判断是否为回归 bug；历史工单（`zendesk_search`）查看是否有已知问题
- **交叉验证**：用官方文档或 Zendesk KB 确认预期行为，与代码实际行为对比

### 分析重点

- 必须创建 worktree，不要依赖 `git_grep` / `git_show` 做主分析
- 搜索命中后，至少追踪 **2 层调用链**（调用方 → 当前函数 → 被调用方），不要只看单个文件就下结论
- 如果客户报告"升级后出现"，**必须用 `git_diff` 对比新旧版本**，定位引入问题的具体 commit 或变更
- 关注异常处理路径：很多 bug 出在 error handling 分支而非主流程
- 前后端关联问题需要同时查看 API 端和前端调用代码
- **确认 bug 后，必须检查新版本是否已修复**：用 `list_repo_tags` 查看最新的几个 tag，再用 `git_diff` 或 `git_show` 对比客户版本与最新版本中同一文件的差异。如果新版本已修复，直接告知客户升级即可；如果未修复，说明该问题仍然存在

### 回复要求

- 回复必须包含代码证据（精简代码片段 + 说明该片段如何证明结论）
- 如果确认是 bug，说明影响范围（哪些版本受影响、哪些场景会触发）
- **如果新版本已修复**：明确给出修复版本号，说明客户可以升级解决，并简述修复内容
- **如果新版本未修复**：提供 workaround（如有），说明该问题在最新版本中仍存在
- 提供建议的修复方向（无论是否已修复，帮助客户理解问题本质）
