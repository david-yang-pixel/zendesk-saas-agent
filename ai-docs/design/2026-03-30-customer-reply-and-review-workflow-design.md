# 客户回复建议与复核工作流设计

**创建时间：** 2026-03-30
**状态：** 已确认

---

## 背景

当前 zd-agent 的主产物是发给内部看的 `Internal Note`。这已经能覆盖问题理解、分析结论和处理建议，但在实际支持流程里仍有两个明显缺口：

- 缺少一段可直接给支持同学参考的“客户回复建议”，导致内部分析还需要人工再转写一遍
- 对代码缺陷类问题，虽然会做源码分析，但没有把“是否已有 PR / commit / 新版本修复”和“人工应该如何复核”固化成必经步骤

这会导致输出停留在“分析过了，但下一步怎么对客户说、内部怎么复核”这一层不够完整。

---

## 目标

- 在最终 Internal Note 中并列产出一段独立的“客户回复建议”
- 对 `code-bug` 类问题新增“修复状态检查”步骤，强制检查本地版本差异与 GitHub PR 状态
- 在最终结果中新增标准化“人工复核指引”，明确告诉 reviewer 要看什么、怎么找、如何判断
- 保持当前 Zendesk internal note 投递模式不变，本次不直接发送 public reply

---

## 非目标

- 本次不新增真正的 Zendesk public reply 发送工具
- 本次不做自动选择“直接发客户”还是“仅内部备注”的分流
- 本次不要求所有工单都必须深查 GitHub PR；该要求只对 `code-bug` 类问题强制生效

---

## 整体方案

保留当前“分析后发送 Internal Note”的主路径，但把最终输出从单段内部回复升级为固定的三段式结构：

```text
Internal Note
├── 内部分析
├── 客户回复建议
└── 人工复核指引
```

同时，在 `code-bug` 策略中新增一个硬性步骤：

```text
源码定位
  → 修复状态检查
    → 本地 tag / commit 差异确认
    → GitHub open / merged PR 检查
  → 生成三段式输出
```

这样可以把“问题为什么发生”“现在修到哪里了”“客户应该收到什么答复”“内部 reviewer 该怎么核实”四件事一次性串起来。

---

## 工作流改动

### 通用输出结构升级

现有 Step 6“生成回复”从单一 Internal Reply 改为固定三段式内容：

1. `内部分析`
2. `客户回复建议`
3. `人工复核指引`

三段都写在同一个 Internal Note 中，由 `zendesk_internal_reply` 统一发送。

### 新增 Step 5.5 — 修复状态检查

该步骤仅在 `classify_ticket` 返回 `code-bug` 时强制执行，放在源码定位之后、生成回复之前。

Agent 必须回答以下四个问题：

1. 客户当前版本中该问题是否存在
2. 比客户版本更新的版本或 `main` 中是否已经修复
3. GitHub 上是否存在相关 `open` 或 `merged` PR
4. 结论属于以下哪一类：
   - `未修复`
   - `修复中`
   - `已合并未发布`
   - `已发布修复`

如果无法确认，也必须明确标注“不确定”，并在“人工复核指引”里说明卡点。

---

## 输出结构设计

### 1. 内部分析

面向支持和研发内部，保留技术细节，建议结构如下：

- 问题确认：复述客户现象与上下文
- 根因判断：说明问题落点，区分已确认与推测部分
- 证据：代码片段、配置、日志、文档或历史工单交叉验证结果
- 影响范围：受影响版本、触发条件、是否为回归
- 修复状态：未修复 / 修复中 / 已合并未发布 / 已发布修复
- 建议动作：升级、workaround、人工介入或继续跟进
- 置信度与风险：低置信度时明确提示

### 2. 客户回复建议

这是写给支持同学复制或改写后发给客户的草稿，必须与内部分析区分表达风格：

- 语言跟随客户最近一条消息的语言
- 不暴露内部推理过程，不使用“我猜测”“我看了源码怀疑”这类措辞
- 如果已修复：明确给出修复版本和建议动作
- 如果未修复：给出当前 workaround，并说明问题仍在处理中
- 如果有开放 PR：可以说明“修复进行中”，但不要承诺不确定发布日期
- 如果需要客户配合：明确写下一步要客户提供什么或执行什么操作

建议模板：

```markdown
## 客户回复建议

Hi <customer>,

We checked the issue and confirmed ...

Current recommendation:
1. ...
2. ...

If needed, please also help provide ...
```

### 3. 人工复核指引

这是标准版 reviewer checklist，不只是列资源名称，还要说明怎么验证。

必须包含：

- 建议查看的 repo
- 建议对比的 tag / branch / ref
- 建议阅读的文件、函数或调用链
- 建议检索的 GitHub PR / issue / commit 关键词
- 判断标准：如何确认“已修复 / 未修复 / 部分修复 / 无关 PR”
- 最小验证路径：如果要人工复现，应优先验证什么场景

建议模板：

```markdown
## 人工复核指引

- Repo: dify / dify-enterprise
- Ref: 客户版本 `x.y.z`，对比 `main` 与最新发布 tag
- Files: api/... , services/... , frontend/...
- GitHub 检索关键词: "<error message>", "<module name>", "<api path>"
- 判断方式: 若客户版本存在该逻辑且最新版本已替换为新分支，则可判定为已修复
- 建议验证: 用同类输入复现一次失败路径，再对比修复后路径
```

## `code-bug` 场景的修复状态检查规则

对于 `code-bug`，现有“看源码 + 看 diff”的流程升级为下面的 checklist：

1. 先在客户版本对应 ref 中定位问题代码
2. 如果客户描述为“升级后出现”，必须对比升级前后版本差异
3. 检查更高版本 tag 或 `main` 中相同文件 / 相同逻辑是否已变化
4. 检查 GitHub 上相关 PR，至少区分：
   - 已合并，且 diff 明确覆盖该问题
   - 已打开，但尚未合并
   - 只有讨论，没有实际修复代码
   - 看似相关，但与本问题无关
5. 最终结论必须落在以下状态之一：
   - `未修复`
   - `修复中`
   - `已合并未发布`
   - `已发布修复`

若 PR 标题相似但没有覆盖同一代码路径，不能判定为已修复。

## 工具能力建议

为了支持上述工作流，工具层至少需要提供以下能力：

### 已有能力可继续复用

- `list_repos`
- `list_repo_tags`
- `git_diff`
- `git_show`
- `sandbox_create_worktree`
- `sandbox_search`
- `sandbox_read`

### 建议新增的 GitHub 能力

如果当前运行环境还不能直接检索 GitHub PR，建议补充最小能力集：

- `github_search_prs(repo, query)`
- `github_get_pr(pr_number)`
- `github_get_pr_files(pr_number)` 或 `github_get_pr_diff(pr_number)`

这些能力只需要支持读取，不要求写入。

- 必查 GitHub open / merged PR
- 必须输出修复状态分类
- 必须给出 reviewer 可执行的复核路径

## 风险与取舍

### 优点

- 内部分析、客户话术、人工复核路径一次产出，减少人工二次加工
- 对 `code-bug` 的支持决策更完整，不再停在“发现 bug”这一步
- 为后续 public reply 能力预留结构，不需要推翻当前设计

### 风险

- 如果 GitHub PR 检索能力不足，模型可能知道“应该查 PR”但无法真正执行
- 三段式输出会让 Internal Note 变长，需要控制内容精简度
- 若 PR 关联判断不严格，可能把“相关讨论”误判成“已修复”

### 应对

- 若暂时没有 GitHub PR 工具，可先把本地 commit/tag 检查做成硬步骤，并在环境具备后接入 GitHub PR 搜索
- 在 prompt 中加入“PR 证据等级”意识，避免过度下结论
- 客户回复建议限制为简洁、可复制的话术，不重复展开所有技术细节

---

## 验收标准

完成后，`code-bug` 类工单的最终 Internal Note 应满足：

- 一定包含 `内部分析`
- 一定包含 `客户回复建议`
- 一定包含 `人工复核指引`
- 一定明确修复状态分类
- 一定说明是否检查过 GitHub PR，以及结论是什么

对于非 `code-bug` 类工单：

- 仍应产出三段式结构
- 但 GitHub PR 检查不是强制项

---

## 后续实施建议

建议按以下顺序实施：

1. 先改 prompt，确保输出结构稳定
2. 再补 GitHub PR 检索工具
3. 最后用真实 `code-bug` 工单回归，验证：
   - 是否能正确判断修复状态
   - 客户回复建议是否可直接使用
   - 人工复核指引是否真的能让 reviewer 快速落地
